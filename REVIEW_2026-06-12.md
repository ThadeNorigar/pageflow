## Executive Summary (30-Sekunden-Lesung)

1. **Keine hartcodierten Secrets im Code.** Die `clientId` in `manifest.yml` ist eine öffentliche OAuth-Client-ID (kein Secret). `.beads-credential-key` ist **nicht** committet. Gut.
2. **KRITISCH (Vertrauen): Die committeten Security-Reports `docs/sca-npm-audit-report.txt` und `sast-eslint-report.txt` sind FALSCH.** Sie behaupten „0 Vulnerabilities, PASS" (Stand 2026-03-10). `npm audit` heute: **17 Vulns gesamt, davon 2 kritisch, 5 hoch.** Production-only: **2 (lodash hoch, brace-expansion moderate).** Die Reports lügen — gefährliche Scheinsicherheit.
3. **HOCH: Storage-Format-Injection in `viewFileMacro`** (`BatchImportPDF.tsx:35`) — der PDF-Dateiname wird **ohne Escaping** in Confluence Storage Format (XML-Makro) eingesetzt. Manipulierter Dateiname kann Markup injizieren.
4. **HOCH: Test-Suite ist ROT.** 5 von 197 Tests schlagen fehl (`fileValidation.test.ts`) — Tests wurden beim i18n-Umbau (DE→EN) nicht mitgezogen. „Grün"-Behauptung im Projekt ist unzutreffend.
5. **MITTEL: Bekannte unfertige Funktion im Prod-Pfad.** `import.ts:39` TODO: Cloud-OneNote-Import lädt Bilder nicht hoch → kaputte Bilder bei jedem Cloud-Import. Selbst als „HIGH Prio" markiert, offen.
6. **MITTEL: Tote/Legacy-Komponenten im Bundle.** `SpaceBrowser.tsx` (deprecated), `FileUpload.tsx` (legacy) werden nirgends verwendet, aber mitgepflegt — `FileUpload` umgeht zudem die Resolver-Schicht (direktes `requestConfluence` aus dem Frontend, widerspricht CLAUDE.md-Regel).
7. **NIEDRIG: Kein Größen-Guard im Backend-Upload.** `attachments.ts` prüft Dateigröße nicht; 10MB-Limit existiert nur im Frontend (umgehbar). Forge-Lambda hat 128MB/25s.
8. **POSITIV: Solides Input-Handling an den wichtigen Stellen.** OneNote-/Page-IDs per Regex validiert, HTML-Konverter mit Tag-/Attribut-**Allowlist** + `href`-Schema-Filter, Multipart-Filename gegen Header-Injection bereinigt. Das ist gut gemacht.
9. **POSITIV: Keine `console.*`-Leaks, kein `eval`/`innerHTML`/`dangerouslySetInnerHTML`, kein `any`-Wildwuchs in Resolvern.** Auth läuft sauber über Forge-Provider, keine selbstgebaute Token-Logik.
10. **Version-Drift:** `getStatus` meldet `version: '0.1.0'` (`resolvers/index.ts:15`) bei App-Version 2.1.0. Kosmetisch, aber Zeichen für fehlende Sorgfalt.

**Gesamteinschätzung:** Architektur und Kern-Sicherheit sind überdurchschnittlich für eine Vibe-Coded App. Die größten Risiken sind **Prozess-/Vertrauens-Probleme** (gefälschte/veraltete Security-Reports, rote Tests als grün dargestellt), nicht tiefe Code-Löcher.

### KRITISCH

#### S-1: Committete Security-Reports sind veraltet/irreführend („0 Vulns / PASS")
- **Datei:** `docs/sca-npm-audit-report.txt`, `docs/sast-eslint-report.txt` (Stand 2026-03-10)
- **Problem:** Beide Reports behaupten „Status: PASS, 0 Findings". Realität heute (`npm audit`):

- **Risiko:** Reports erzeugen falsches Sicherheitsgefühl; bei Marketplace-Review oder Audit ein Glaubwürdigkeits-GAU. lodash im Production-Tree ist real exploitbar, wenn Template-/Path-Funktionen mit Fremddaten genutzt werden.
- **Fix:**
  1. `npm audit fix` laufen lassen, Ergebnis verifizieren.
  2. Statische Report-Dateien entweder löschen oder durch echten, datierten CI-Output ersetzen — niemals manuell „PASS" reinschreiben.
  3. Herkunft von `lodash`/`handlebars` im Prod-Tree prüfen (`npm ls lodash`).
- **Confidence:** 100% (per `npm audit` reproduziert).

### HOCH

#### S-2: Storage-Format-Injection über unescaped Dateinamen in `viewFileMacro`
- **Datei:** `src/frontend/components/BatchImportPDF.tsx:35-37`
- **Code:**
  ```ts
  function viewFileMacro(filename: string): string {
    return `<ac:structured-macro ...><ri:attachment ri:filename="${filename}"/>...`;
  }
  ```
- **Problem:** `filename` (aus lokalem Dateisystem des Nutzers) wird **ohne XML-Escaping** in Confluence Storage Format eingesetzt und via `updatePageBody` gespeichert. Ein Dateiname wie `x"/></ac:parameter></ac:structured-macro><böses-makro>` kann das Markup brechen / fremdes Storage-Format injizieren.
- **Vergleich:** Der OneNote-Konverter macht es richtig (`escapeXml`), `attachments.ts` bereinigt Filenames — hier wurde es vergessen.
- **Risiko:** In geteilten Spaces kann manipuliertes Markup andere Nutzer betreffen (gespeicherte Markup-Injection). Confluence filtert Storage Format beim Rendern teilweise, daher nicht garantiert XSS — aber Markup-Korruption sicher.
- **Fix:** `filename` durch `escapeXml()` jagen (Funktion existiert bereits in `converter.ts` — wiederverwenden, nicht neu bauen).
- **Confidence:** 70% (exploitierbar; ob es bis zu aktivem XSS reicht, hängt von Confluence-Rendering ab).

#### S-3: Test-Suite rot — Sicherheits-/Validierungstests schlagen fehl
- **Datei:** `tests/frontend/fileValidation.test.ts` (5 Failures)
- **Problem:** Tests erwarten deutsche Fehlermeldungen (`"… ist keine PDF-Datei"`), Code liefert englische (i18n-Commit `3e9fbb6`). Die Tests wurden nicht angepasst → **Suite ist rot, aber das Projekt wird als release-fertig behandelt** (v2.1.0 „prepared").
- **Risiko:** Rote Tests = niemand merkt, wenn die Datei-Validierung (Security-Boundary: PDF-Typ + 10MB-Limit) tatsächlich bricht. Verstößt gegen „kein fertig ohne grüne Tests".
- **Fix:** Erwartungswerte in `fileValidation.test.ts` auf EN-Strings angleichen, dann `npm test` grün verifizieren.
- **Confidence:** 100% (reproduziert: `Tests: 5 failed, 192 passed`).

### MITTEL

#### S-4: Kein Backend-seitiger Größen-/Inhalts-Guard beim Attachment-Upload
- **Datei:** `src/resolvers/confluence/attachments.ts:15-37`
- **Problem:** 10MB-Limit & PDF-Typprüfung leben nur im Frontend (`fileValidation.ts`). Der Resolver `uploadAttachment` nimmt beliebige Base64-Größe/MimeType an. Frontend-Validierung ist umgehbar (direkter `invoke`).
- **Risiko:** DoS/Lambda-Crash (128MB Memory, 25s Timeout) durch übergroße Payloads; Upload beliebiger Dateitypen.
- **Fix:** Größen-Check (`Buffer.byteLength`) und ggf. MimeType-Allowlist im Resolver ergänzen.
- **Confidence:** 90%.

#### S-5: `FileUpload.tsx` umgeht Resolver-Schicht (direktes `requestConfluence` aus Frontend)
- **Datei:** `src/frontend/components/FileUpload.tsx:103`
- **Problem:** Direkter `requestConfluence`-Call aus dem Frontend statt über Resolver. Widerspricht der eigenen CLAUDE.md-Regel und der Backend-Validierungsstrategie. Komponente ist zwar (siehe P-1) ungenutzt/legacy, aber im Repo.
- **Risiko:** Inkonsistente Security-Boundary; falls reaktiviert, kein zentraler Validierungspunkt.
- **Fix:** Komponente löschen (siehe P-1) oder auf Resolver umstellen.
- **Confidence:** 85%.

### NIEDRIG

- **Confidence:** 50% (evtl. funktional nötig).

- **Confidence:** 100%.
